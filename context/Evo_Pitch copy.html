AML Alert Triage System

A full-stack, AI-augmented Anti-Money Laundering triage platform that combines rule-based alert generation, a 4-agent LLM pipeline, and a human-in-the-loop analyst review interface — with continuous feedback-driven rule recalibration.

Frontend React 19 + TypeScript (Vite)
Backend FastAPI + Python 3.13
Database SQLite (aml_triage.db)
LLM Provider AWS Bedrock (Claude)
Transactions 24,999 raw records
1

System Overview

The application is a React + FastAPI system that automatically triages AML (Anti-Money Laundering) alerts using a 4-agent LLM pipeline, then presents those outputs to a human analyst for a final verdict. Analyst decisions feed back into an Evolution Agent that recalibrates detection rules over time, creating a continuously improving feedback loop.

💡
Architecture Philosophy

The system is intentionally designed as human-in-the-loop: the AI pipeline triages and prioritises, but a licensed analyst always makes the final SAR/escalation decision. The Evolution Agent learns from analyst overrides to tune detection thresholds over time.

⚠️
Alert Count vs Transaction Count

A single transaction can trigger multiple detection rules, producing multiple independent alerts. This is why total_alerts > total_transactions in the database. Each alert is triaged independently through the full pipeline.

Alert Generation — backend/services/alert_generator.py

Eight detection rules scan all 24,999 transactions and create PENDING alerts in both the in-memory registry (_alert_registry in main.py) and SQLite (aml_triage.db). Rules operate at transaction-level, meaning one transaction can trigger multiple rules simultaneously.

Rule ID Trigger Condition Risk Signal Category
RULE_HV Transaction value > AUD 10,000 High-value cash movement threshold Volume
RULE_CRYPTO Transaction type = Cryptocurrency Pseudonymous asset conversion Asset Type
RULE_PEP Customer flagged as Politically Exposed Person Elevated corruption/bribery risk Profile
RULE_DECEASED Transaction date > customer's deceased date Identity fraud / estate fraud Identity
RULE_DORMANT Activity after 12+ month inactivity gap Account takeover / reactivation risk Behaviour
RULE_MULTI_CCY 3+ currencies within a 30-day window Layering / currency conversion chains Pattern
RULE_CASH Cash > 50% of 30-day transaction volume Cash-intensive structuring / smurfing Volume
RULE_FOREIGN_WIRE Non-AUD wired transfer Cross-border fund movement Wire
ℹ️
Rule Engine is Synchronous

Alert generation runs as a pure Python synchronous scan — no LLM involvement. This keeps initial alert creation fast and deterministic. All 8 rules are evaluated independently per transaction, and all matches are persisted immediately.

Triage Pipeline — backend/agents/orchestrator.py

Each PENDING alert passes through 4 sequential agents. Status transitions are written to both the in-memory registry and SQLite at each step. On any agent failure, the alert's status becomes ERROR with an error_message field populated.

💾
Persistence

All 4 agent outputs are merged and stored as a single triage_result_json blob in SQLite. The JSON schema is: { risk_assessment, categorisation, investigation_summary }. Enrichment output (enriched_context) is used as pipeline input but is not separately persisted.

🔴
Error Handling

On any agent failure (LLM timeout, parsing error, Bedrock rate limit), the alert status transitions to ERROR and error_message is populated. The alert is not retried automatically — a manual re-triage or batch restart is required.

5

Auto-Label — backend/agents/agent0_autolabel.py

Agent 0 runs on startup and after each batch triage. It scores completed alerts without any LLM call using deterministic heuristic rules applied to triage_result fields. The goal is to pre-sort alerts so analysts can prioritise TRUE_POSITIVE candidates first.

Scoring Weights (additive)

+0.50 if primary_typology == "LOW_RISK" — strongest single indicator of false positive
+0.30 if recommended_action == "CLOSE" — LLM recommended no further action
+0.20 if confidence < 0.4 — LLM categorisation confidence is low (ambiguous signal)
+0.10 if investigation confidence_level == "LOW" — summary agent also uncertain
📐
Score Interpretation

A higher fp_probability score means the alert is more likely to be a false positive. Max possible score is 1.10 (all conditions true). The score is not normalised to 1.0 by design — the heuristic weights are calibrated against observed analyst verdicts during system tuning.

Score Scale Inconsistency — Known Issue (Partially Fixed)

Seeded alerts (seed_rich_alerts.py) store risk scores as integers 0–100. LLM-triaged alerts store scores as floats 0–1. The UI normalises at render time:

score > 1 ? score : score * 100

This fix exists in both ScoreBar.tsx and AlertLabelModal.tsx. The underlying DB values are not normalised — mixing will persist until a migration script is written to standardise all seeded scores to 0–1.

Analyst Verdict Submission

When an analyst clicks one of the three verdict buttons in the modal, a feedback POST is issued to the backend. The backend writes the verdict to SQLite immediately, and the UI updates local state without requiring a full page reload.

API Endpoint
POST /api/alerts/{alert_id}/feedback // Request Body { "verdict": "FALSE_POSITIVE" // | "TRUE_POSITIVE" | "INCONCLUSIVE" "notes": "Optional analyst notes..." "override_action": "CLOSE" // | "REVIEW" | "ESCALATE" | null } // Database columns written: analyst_verdict → verdict value analyst_notes → notes string feedback_submitted_at → UTC timestamp
⚡
Optimistic UI Update

handleGroupUpdated in LabelingPage.tsx updates local component state immediately upon successful API response — without triggering a full data refetch. This keeps the analyst workflow fast and responsive, particularly important when triaging large queues.

🔁
Feedback Loop to Evolution Agent

Each submitted verdict is consumed by Agent 5 (Evolution Agent) during recalibration runs. The agent uses the delta between predicted_verdict (auto-label) and analyst_verdict (ground truth) to adjust detection rule thresholds. A large divergence on a specific rule triggers threshold re-tuning for that rule.

Known Issues & Tech Debt

The following issues are tracked and understood. Each entry includes the affected location, current status, and recommended resolution path.

Score Scale Mixed (0–1 vs 0–100) in Database
seed_rich_alerts.py (seeded) ↔ LLM agents (0–1 float)
Seeded alerts use integer 0–100 scores; LLM-triaged alerts use float 0–1 scores. Both coexist in the same SQLite columns. UI normalises at render time via score > 1 ? score : score * 100, but this does not fix the underlying data. Long-term fix: write a migration to standardise all seeded scores to 0–1 floats.
UI Fixed Only
Batch Triage Times Out Through Cloudflare Tunnel
main.py:376 — 200 concurrent LLM calls
When triggering a full batch triage (all PENDING alerts), the system fires up to 200 concurrent asyncio.to_thread LLM calls. Cloudflare's 100-second request timeout kills the connection before the batch completes. Fix options: (1) reduce batch size to ≤50 alerts per call, or (2) implement an async background job pattern with polling endpoint so the client doesn't need to hold the connection open.
Needs Fix
In-Memory Registry Not Persisted — Restart Requires DB Reload
main.py:62–74 — _alert_registry dict
The in-memory _alert_registry is populated from SQLite on startup. Any PENDING alerts added after startup (e.g. via API during runtime) live only in memory and are invisible after a backend restart until a DB reload is triggered. This is by design for the demo context, but could cause silent data loss in a production environment with high-frequency alert generation.
By Design
Dashboard Stats Don't Auto-Poll
DashboardPage.tsx:44 — single fetch on mount
Dashboard statistics (alert counts, pipeline status, verdict distribution) are fetched once on component mount and never refreshed. If alerts are being triaged in the background while the analyst is viewing the dashboard, numbers will be stale until manual page refresh. Fix: add a setInterval polling hook (e.g. 10s) or a WebSocket push.
Needs Fix
Demo Reset Clears Memory Only — Not SQLite DB
main.py:138–149 — reset endpoint
The demo reset endpoint flushes _alert_registry in memory but does not execute a DELETE FROM alerts in SQLite. On next startup, the DB-populated registry will re-load the supposedly "reset" alerts. Fix: have the reset endpoint also wipe the SQLite table, or document clearly that a full reset requires both the endpoint call AND manual DB deletion.
By Design
🔧
Priority Fix Order

1st — Batch timeout (blocks full pipeline runs) → 2nd — Dashboard polling (analyst experience) → 3rd — Score normalisation migration (data integrity) → 4th — Memory/DB divergence (production hardening)

Warning: --clear is irreversible

The --clear flag deletes all rows from the alerts table in SQLite before seeding. There is no confirmation prompt and no backup is taken. In a demo or staging environment this is acceptable, but ensure no analyst-submitted verdicts need to be preserved before running with this flag.

11

Evolution Agent & Recalibration Loop — Next Steps

The Evolution Agent closes the feedback loop between analyst verdicts and the detection engine. The changes below extend the existing Agent 5 concept into a fully operational recalibration system with per-rule threshold learning, iteration tracking, and a one-click UI trigger. Everything described here is Planned / In Progress unless otherwise noted.

🔁
How the Loop Works

Analyst verdicts accumulate in SQLite → /recalibrate computes new per-rule FP/TP thresholds from observed label distributions → thresholds are written to the rule_weights table → Agent 0 loads the new thresholds on its next run → /recalibrate-and-relabel does all of the above then immediately re-scores every AUTO_UNCERTAIN alert with the updated thresholds → autolabel_runs records each iteration's statistics for trend visualisation.

11.1 — New Backend Endpoints
POST /recalibrate

Reads all alerts with an analyst_verdict, groups them by triggering rule, and computes observed FP and TP rates per rule. Writes the resulting thresholds to the new rule_weights table. Does not re-run auto-label.

// Response shape { "status": "ok", "rules_updated": 8, "run_id": "evo_run_003", "thresholds": { "RULE_HV": { "fp_threshold": 0.61, "tp_threshold": 0.28 }, "RULE_DORMANT": { "fp_threshold": 0.55, "tp_threshold": 0.22 }, // ... one entry per rule } }
POST /recalibrate-and-relabel

Atomic two-step operation: runs /recalibrate first, then immediately re-executes Agent 0 auto-label on all AUTO_UNCERTAIN alerts using the freshly written per-rule thresholds. Returns before/after counts so the UI can render the shrink delta.

// Response shape { "status": "ok", "run_id": "evo_run_003", "before": { "auto_fp": 142, "auto_tp": 87, "uncertain": 203 }, "after": { "auto_fp": 168, "auto_tp": 109, "uncertain": 155 }, "relabeled_count": 48 }
11.2 — New Database Tables
📋 rule_weights

Stores per-rule thresholds computed by each recalibration run. Agent 0 reads the most recent row per rule on startup. Falls back to global defaults (fp ≥ 0.65 / tp ≤ 0.25) if the table is empty or a rule has no data.

CREATE TABLE rule_weights ( id INTEGER PRIMARY KEY, run_id TEXT NOT NULL, rule_id TEXT NOT NULL, -- e.g. "RULE_HV" fp_threshold REAL NOT NULL, -- above → AUTO_FP tp_threshold REAL NOT NULL, -- below → AUTO_TP sample_size INTEGER NOT NULL, -- labeled alerts used observed_fp_rate REAL, -- raw FP% in sample created_at TEXT DEFAULT (datetime('now')) );
📊 autolabel_runs

Records a snapshot of FP / TP / UNCERTAIN counts after every Agent 0 execution. Each row is one iteration. Used by the Evolution page to render the trend line and uncertain-shrink bar chart across runs.

CREATE TABLE autolabel_runs ( id INTEGER PRIMARY KEY, run_id TEXT NOT NULL, -- e.g. "evo_run_003" triggered_by TEXT, -- "startup"|"recalibrate"|"manual" auto_fp_count INTEGER NOT NULL, auto_tp_count INTEGER NOT NULL, uncertain_count INTEGER NOT NULL, total_labeled INTEGER NOT NULL, -- analyst verdicts available created_at TEXT DEFAULT (datetime('now')) );
11.3 — Agent 0 Modifications (agent0_autolabel.py)

Agent 0's scoring logic is unchanged — the heuristic weight table (+0.50 / +0.30 / +0.20 / +0.10) remains identical. Only the classification threshold step is updated to be rule-aware.

Before — Global Thresholds
# Hard-coded globals — same for all rules FP_THRESHOLD = 0.65 TP_THRESHOLD = 0.25 if fp_probability >= FP_THRESHOLD: verdict = "AUTO_FP" elif fp_probability <= TP_THRESHOLD: verdict = "AUTO_TP" else: verdict = "AUTO_UNCERTAIN"
After — Per-Rule Thresholds
# Load from rule_weights, fallback to globals weights = load_rule_weights(db, rule_id) fp_t = weights.fp_threshold or 0.65 tp_t = weights.tp_threshold or 0.25 if fp_probability >= fp_t: verdict = "AUTO_FP" elif fp_probability <= tp_t: verdict = "AUTO_TP" else: verdict = "AUTO_UNCERTAIN"
🔁
Fallback Behaviour

If rule_weights is empty (fresh install, or no recalibration run yet), Agent 0 silently falls back to the global thresholds (0.65 / 0.25). This means the system is always functional even before any analyst verdicts have been submitted. No configuration change is required after a fresh seed.

11.5 — Implementation Notes & Caveats
Minimum Labeled Alerts Required Before Recalibration Is Useful
POST /recalibrate — threshold computation logic
Recalibration produces meaningful thresholds only when sufficient analyst verdicts have been submitted. Recommendation: require at least 30 total labeled alerts (across all rules) before enabling the button, and at least 15 per rule for that rule's threshold to update. Surface in the UI: "23 / 30 verdicts needed to unlock recalibration."
To Implement
Re-label Scope: AUTO_UNCERTAIN Only
POST /recalibrate-and-relabel — Agent 0 re-run scope
The endpoint re-runs Agent 0 only on AUTO_UNCERTAIN alerts to avoid churning stable classifications. A full re-label (all COMPLETE alerts) can be triggered via a planned ?scope=all query parameter if a threshold change is large enough to warrant it.
By Design
Threshold History Is Append-Only
rule_weights table — no UPDATE, only INSERT
Each recalibration run inserts new rows rather than updating existing ones. Agent 0 always reads the row with the latest created_at per rule. This gives a full audit trail and allows rollback by deleting the most recent run's rows. Do not add ON CONFLICT REPLACE — it would destroy the history.
By Design
Dashboard Page Needs autolabel_runs Hook
DashboardPage.tsx — existing single-fetch stats
The existing dashboard fetch (single mount, no polling — see Section 9) also needs to read from autolabel_runs to display the current run iteration number and total uncertain count. Add a GET /api/evolution/summary endpoint returning the latest run stats, included in the dashboard mount fetch.
To Implement
