01 / Boundaries

Preserve the feedback loop. Keep execution small.

The use case is investigation assistance for an AML analyst and monitoring lead. The system turns rule matches into evidence-backed briefs, captures analyst judgments, and studies the resulting decisions and execution costs. Alert generation, model predictions, analyst judgments, and synthetic reference labels remain separate.

Interaction layer

React + TypeScript interface. Public visitors inspect a frozen read-only demo. An authenticated operator can triage, review, analyze, evaluate, and publish.

Execution layer

One FastAPI codebase, one image, two Cloud Run deployment modes: public API/web and private worker. Plain Python orchestration; no agent framework required.

Data layer

Cloud Firestore, Standard edition in Native mode, plus Firebase Authentication. Firebase is the product platform; Firestore is the chosen database. Realtime Database is unnecessary.

Cloud Run, Cloud Tasks, and Firestore default to australia-southeast1. The Google-managed Gemini endpoint uses global, with fictional data only. Baseline model: gemini-3.5-flash, subject to a credited-project smoke test. The browser receives no model credentials.

Scope lock: Evolution suggests changes and runs isolated evaluations. The hackathon has no activation endpoint, autonomous rule changes, prompt self-editing in production, regulatory filings, account freezes, or transaction blocking. A reviewed proposal is not an applied upgrade.

“Agent skills” here means versioned task instructions, permitted tools, input/output schemas, and refusal/abstention rules within this application. It does not mean installing editor plugins or granting the AI new permissions.

02 / Container and data flow

Two services. One bounded workflow.

People & screens

Judge → read-only published dashboard / queue / investigation / evolution.
Operator → Firebase Google sign-in → same screens with verified action controls.

↓ HTTPS / verified identity
Public web / API

FastAPI serves the built React application. Authorize every operator command; validate payload; persist job; dispatch task. Public routes serve explicit sanitized snapshots only.

↓ Cloud Tasks / OIDC identity
Private worker

Claim a job with a lease. Run A1 → A2 → A3 → A4 → A0; checkpoint each validated output. Separate jobs run aggregation → A5 or simulation/evaluation. The model gateway enforces budgets and logs attempts.

↓ SDK access using service IAM
Firestore & Gemini

Firestore holds immutable evidence, versioned runs, labels, proposals, and cost records. Gemini receives only leg-specific context. Cloud Logging holds redacted operational logs, not the authoritative application ledger.

Agent contracts

  • A1: 90-day customer/account trail; 30-day rolling statistics; explicit older last-activity metadata. Exclude future records and distinguish missing history from zero activity.
  • A2: transaction, customer, account, behavioral, network dimensions. Gemini explains code-computed scores; it cannot overwrite them.
  • A3: taxonomy: STRUCTURING, LAYERING, SANCTIONS_EXPOSURE, POTENTIAL_IDENTITY_MISUSE, PEP_REVIEW, LOW_RISK, OTHER, UNDETERMINED. Suggested actions: ESCALATE, REVIEW, MONITOR, CLOSE. None is an executed banking action.
  • A4: overview, context, key findings with citations, benign explanations, missing information, next steps, limitations. Maximum 500 words.
  • A0: missing context / failed validation → NEEDS_CONTEXT; protected signal, high risk, or escalation → URGENT_REVIEW; complete low risk with CLOSE suggestion → LOWER_PRIORITY; otherwise STANDARD_REVIEW. On a failed earlier leg, the orchestrator records NEEDS_CONTEXT without pretending A0 completed.
  • A5: two analytical inputs: human-feedback quality and execution economics. It may propose detector, prompt, skill, context, or risk-policy changes. It does not retrain a model or alter the baseline.

04 / Mathematical binding

Bind the facts, score, context, and objective explicitly.

1. Evidence-to-leg binding

Cᵢ = Project(EvidenceSnapshot, ContextPolicyᵢ, Budgetᵢ)
Yᵢ = Validate(Model(Promptᵢ, Skillᵢ, Cᵢ, UpstreamFacts), Schemaᵢ, EvidenceIDs)
BindingID = SHA256(dataset + evidence hash + configuration bundle + prompt/input hashes)

The bundle pins all component versions at enqueue time. Changing a current configuration file cannot change an in-flight run. Every cited identifier must belong to that run’s selected evidence; cross-case references fail validation. A valid identifier alone does not establish that a sentence is supported.

2. Risk-score binding

R = 0.30 × transaction + 0.25 × customer + 0.15 × account + 0.20 × behavioral + 0.10 × network
0 ≤ dimension ≤ 1; weights ≥ 0; Σweights = 1

Each dimension takes the maximum applicable versioned signal score, otherwise 0.1. Required missing inputs yield an unavailable score, not a zero and not a silently renormalized formula. Tiers: LOW <0.3, MEDIUM <0.5, HIGH <0.7, otherwise CRITICAL. Synthetic sanctions exposure, structuring, and post-death signals independently prevent lower-priority treatment.

DimensionInitial demo signal mapping
TransactionStructuring 1.0; high value 0.7; cash intensity 0.6; crypto 0.5.
CustomerSynthetic sanctions 0.9; PEP 0.6; customer age <180 days 0.2.
AccountPost-death 0.9; dormant reactivation 0.8; account age <90 days 0.3.
BehavioralStructuring 0.8; threefold count increase over prior comparable 30-day window 0.6; multiple currencies 0.5. No baseline gives unknown, not infinite velocity.
NetworkSynthetic counterparty sanctions 0.9; three new counterparties in 24h 0.7; foreign wire 0.4.

Scores are transparent prototype heuristics. They are not calibrated probabilities, statutory thresholds, or evidence of criminal conduct.

Illustrative input only; no observed model or detection results.

Changing inputs here changes no application settings and proves no improvement. A weight-change proposal requires a paired evaluation.

3. Cost/quality objective

J(θ) = 0.50 × (Costθ / Costbaseline) + 0.20 × (p95Latencyθ / p95Latencybaseline)
+ 0.30 × (FPRθ / max(FPRbaseline, 0.01))
θ = {context policy, prompt, skill, risk weights}; choose the lowest J among candidates that pass every quality gate.

These are explicit initial engineering preferences, not learned facts or competition scoring weights. Reject optimization when cost coverage, baselines, or denominators are unavailable; report separate metrics instead. Cost includes the changed workflow’s downstream calls and failed/retried attempts. Lower context tokens alone is only a proxy for savings.

Hard gates before ranking: no additional missed suspicious cases on the paired population; recall at least baseline; at least one predicted positive before claiming precision; precision no worse than baseline; no increased abstention count or validation failures; all citation IDs valid; manually reviewed evidence-support rate not below baseline; no protected-field loss. Unavailable evidence gives INSUFFICIENT_EVIDENCE, not PASS.

Risk weights stay nonnegative and sum to 1. Evolution may propose a small one-variable change; a deterministic evaluator validates the proposal and computes all metrics. With a small synthetic sample, passing means only “passed this demo evaluation.”

Budgets include instructions and serialized schemas. Generated-token configuration must account for any model-specific thinking budget; record actual provider usage separately. These are initial caps to validate in the model smoke test, not measured utilization.

  1. Build exact features from the full applicable history before selecting excerpts.
  2. Attach a compact fact registry: fact ID, value, unit, time window, source IDs.
  3. Select evidence deterministically: trigger first, protected sequences, counter-evidence, then remaining relevance-ranked records with timestamp/ID tie-breaking.
  4. Retain all records needed to understand a structuring sequence, relationships and chronology. Never summarize away a protected signal to fit a budget.
  5. Pre-count the exact serialized request using the provider’s supported token-count method. A character heuristic is only a preliminary bound.
  6. If essential context cannot fit, mark CONTEXT_BUDGET_EXCEEDED / NEEDS_CONTEXT and request review. Do not silently truncate.

The context snapshot records retained and omitted IDs, policy version, count, reasons for omission and input hash. The investigator can still open authoritative records that were not sent to Gemini. Context savings must be tested against the same baseline cases; compression does not itself establish quality.

Reference: Google token-count guidance. Provider response usage is the accounting input; pre-counts are estimates for admission control.

06 / Database contract

18 collections. Explicit document links.

Firestore stores documents in collections, not SQL tables. The specification below is the DDL equivalent: identifiers, fields, constraints, relationships, write ownership and indexes. It does not create a database or automatically enforce schemas. Implement the contract in Pydantic and repository functions. Firestore data model.

All are root collections in one small demo database. The primary key is the document ID. Every dataset-scoped record carries dataset_id; backend reads verify matching scope. This is a single-project prototype, not a tenant-isolation design.

datasets → customers → accounts → transactions
    └────→ cases → alerts → pipeline_runs → step_runs
                       │       │                │
                       │       └→ child runs    └→ usage + versions + evidence
                       └→ feedback_events
feedback_events + step_runs + evaluations → evolution_runs → patterns
evolution_runs → recommendations → candidate config_versions
recommendations → evaluations / simulations → human review
validated source runs → publications → public read-only interface
all mutations → audit_events     model attempts → usage_daily reservations

Shared fields: schema_version, created_at (UTC Firestore Timestamp), created_by, and a canonical content_hash for sealed payloads. ? denotes an optional/nullable field. Arrays are bounded for the 112-case prototype; do not append indefinitely.

07 / Link tables, invariants and indexes

The run records are the linkage records.

No SQL join tables are needed. pipeline_runs links alert/case, parent work, frozen bundle and outputs. step_runs links one attempt to evidence, versions and usage. feedback_events links a human decision to the exact triage run. evaluations links baseline/candidate versions to a frozen population. These records provide the practical many-to-many lineage through bounded manifests and named IDs.

InvariantImplementation contract
Stable alertsHash dataset + trigger transaction + rule. Rescanning cannot create a duplicate, regardless of completion.
Feedback consistencyTransaction checks expected feedback_revision, creates a new event, advances alert revision, writes audit event. Older event remains intact.
Run reproducibilityFreeze input and component bundle IDs before dispatch. Retry resumes immutable checkpoints. New configuration produces a new run.
Usage admissionTransaction creates STARTED step attempt and reserves its ID in usage_daily before any network call; no external calls inside transaction callbacks.
Attempt finalizationOne terminal update with output, usage and audit event. Unknown network outcome remains UNKNOWN_OUTCOME with null usage; never assume exactly-once provider execution.
Snapshot identitySorted feedback IDs + cutoff + dataset + versions yield a snapshot hash. Same snapshot does not increase pattern evidence.
ReferencesReject missing parents, cross-dataset links and orphan references at write boundaries; no native foreign keys or cascade deletes assumed.
Version immutabilityConfigurations identified by content hash. Candidate changes create new documents; baseline component bodies never overwritten.

Firestore supports transactional writes, but transaction callbacks can retry. Keep model calls, queue dispatch and external side effects outside them. Transactions guidance.

Attempt lifecycle

  1. Confirm credits, kill switch, operator permission and UTC daily limit of 120 model attempts.
  2. Atomically reserve an attempt and create STARTED record; close the transaction.
  3. Construct exact context, check input/output limits, call Gemini.
  4. Persist validated output and provider-reported usage, or failure/unknown status; finalize audit event.
  5. If a transient retry is permitted, reserve a new attempt linked to the first. One retry maximum at the gateway. Checkpoints avoid replaying already successful legs.

A crash after a provider response but before persistence can leave cost unknown; mark it explicitly and reconcile with provider/billing evidence where available. A daily reservation remains spent even if the response is lost. No design can infer a missing bill from a timeout.

09 / Evolution is a proposal system

Learn from outcomes and economics without self-modification.

Detection / quality

Compare human decisions with suggestions, identify noisy rules, study false negatives using independent reference cases, and propose limited rule or scoring experiments.

Context / efficiency

Compare tokens and retries by role. Propose removing duplicate fields, using fact registries, or moving calculations into deterministic code.

Prompt / skill

Suggest a specific instruction/schema/tool-policy diff with supporting failure IDs, expected benefit, risks and an evaluation plan.

What a proposal contains

base bundle → candidate bundle
change type → one changed component
reason → observed feedback / usage / evaluation IDs
hypothesis → expected direction, not promised percentage
preserved fields → protected evidence and permissions
evaluation plan → population, mapping, gates, call budget
result → measured deltas, failures and coverage
human decision → reviewed / rejected + note
  1. Freeze latest eligible feedback revisions and matching attempts at a cutoff. Keep synthetic scripted labels visibly separate from live operator decisions.
  2. Compute counts, rates, token distributions, latency, retries, validation errors and usage coverage in code. Require 30 conclusive reviewed alerts overall and 15 per rule for a detector proposal. These are prototype sufficiency gates, not statistical validity claims.
  3. Provide A5 compact statistics and representative evidence. It can inspect its previous evaluations and its own completed usage on a subsequent run, not the current invocation’s future usage.
  4. Generate an allowlisted candidate. Prompt/skill changes are bounded instruction/schema changes; context candidates alter selection/budgets; risk candidates alter nonnegative normalized weights. No generated code, expanded permissions, hidden model tools or mutation access.
  5. Save candidate versions, origin=EVOLUTION_CANDIDATE, and proposal links. Do not overwrite active/baseline versions.
  6. Evaluate one component at a time against the same population, rerunning all affected downstream roles. Cheap schema/text checks precede any paid replay.
  7. Present measured tradeoffs for human review. No deployed update follows REVIEWED. Optional export is a development artifact for a separately authorized release.

Allowed detector candidates for v1

High-value threshold → AUD 15,000 or 20,000; or expected-activity exemption for accounts at least 365 days old, at least 30 comparable historical transactions, amount within two standard deviations, and no protected signals. The server enumerates candidates; A5 explains/ranks them. Detector rules are demo settings, not regulatory reporting rules.

Do not reduce “false positives” merely by relabeling alerts, lowering uncertainty or suppressing an entire rule without checking cases retained by other rules. An apparent improvement can be a change in review population.

Version policy: initial BUNDLE IDs are configured by the deployment. The hackathon exposes no active-version promotion endpoint. A future approved release would pin a new bundle, preserve earlier runs, and roll back by selecting the prior bundle in a new release—not deleting history.

10 / Independent evidence

Protect the denominator and the held-out split.

Create 112 fresh fictional case bundles: 60 calibration (40 discovery / 20 candidate selection), 40 held-out, 12 demo. Customers and scenario variants are disjoint. Freeze the manifest and label provenance before looking at candidate results. Only discovery feedback reaches the proposal model.

Place at least 30 high-value examples, including benign and suspicious cases, in discovery so detector proposals have enough support. Show all label provenance: synthetic reference, synthetic scripted review, and human operator feedback are different things.

MetricDefinition / boundary
Rule detection TP / FP / FN / TNCase is predicted positive if any detector rule retains an alert; compare against frozen reference labels. Include negative cases with no alerts to obtain TN and FN.
AI-assisted triage metricsSeparate from detector metrics. On complete cases, predicted positive if any alert suggests ESCALATE/REVIEW; negative only when all suggest MONITOR/CLOSE. Missing/failed/inconclusive output → abstention. Report this mapping and counts.
Precision / recall / FPRTP/(TP+FP); TP/(TP+FN); FP/(FP+TN). Null for zero denominator. Report abstentions separately and effective suspicious-case coverage including abstentions.
Alert-noise proportionBenign labeled alerts / conclusive labeled alerts. This is not population FPR. Counts of alerts and cases cannot be interchanged.
Context reduction(Baseline prompt tokens − candidate prompt tokens) / baseline prompt tokens on the same cases; pair by case and include unknown coverage.
GroundingAll cited IDs must be valid. Manual evidence-support checks assess whether claims follow from those records. At least five paired cases including protected/counter-evidence cases for the minimum smoke check.
Cost / latencyTotal attempt cost, known/unknown coverage, p50/p95 end-to-end latency, retries; compare complete workflows, not only one smaller prompt.

For recall safety, do not exclude suspicious cases that abstain: report effective recall as detected suspicious cases divided by all reference-suspicious cases. A candidate cannot improve the objective by abstaining on difficult examples. Freeze detector and AI mapping versions in evaluations.

Experiment procedure

  1. Use discovery for hypotheses; candidate selection uses only the 20 calibration-selection cases.
  2. Choose one candidate, record the candidate hash, and seal it before accessing the 40 held-out outcomes.
  3. Compare paired results on the same frozen cases with the same model, FX policy and prediction mapping. Change one component only.
  4. Require no additional suspicious-case misses, no worse effective recall or precision, no increased abstentions/validation failures, no protected-context loss, valid citations, and non-degraded manually checked evidence support.
  5. If any hard gate fails, mark FAIL. If evidence, cost mapping or labels are insufficient, mark INSUFFICIENT_EVIDENCE. Only then rank passing candidates by the cost/quality objective.
  6. Record held-out results once. Do not revise the candidate against that split and still call it held out. New tuning requires a new evaluation population.

False negatives cannot be found by studying flagged alerts alone. The synthetic evaluation population must include non-alerted suspicious cases. Similar caution applies to “improved true positives”: raising TP count without checking recall, precision and population size is not sufficient.

The few-day minimum is one complete investigation plus an Evolution proposal and deterministic held-out detector simulation. Prompt/skill/weight proposals can be drafted and inspected immediately; a claim that they improve performance requires credited, paired model replay. Unrun experiments remain explicitly UNEVALUATED.
