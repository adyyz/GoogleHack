SECTION 1 — THE PROBLEM WE ARE SOLVING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Every AML system shares the same painful truth: the majority of the alerts it
raises are false positives. Industry benchmarks put this figure at 85–95%. That
means for every 100 alerts a compliance analyst opens, 85 to 95 of them turn out
to be legitimate customer behaviour — salary payments, routine business transfers,
or a person simply making their first international wire.

The cost of this noise is enormous:
  • Analysts spend hours reviewing alerts that lead nowhere.
  • True threats get buried under the volume of irrelevant ones.
  • Compliance teams scale headcount just to keep up, not to get smarter.

The root cause is that traditional AML rule engines are static. They are
configured once, calibrated in isolation, and then left to drift. They cannot
observe what happened after the alert was raised. They cannot ask: "Was I right?"
They have no memory.

The Evolution Agent solves exactly this.

SECTION 2 — WHAT THE EVOLUTION AGENT IS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The Evolution Agent (Agent 5) is the sixth and final agent in our agentic
pipeline. It is distinct from the other five in one critical way:

  Every other agent operates on a single alert.
  The Evolution Agent operates on the accumulated history of ALL alerts.

It is a closed-loop learning agent. It watches every analyst verdict — every time
a human says "TRUE_POSITIVE", "FALSE_POSITIVE", or "INCONCLUSIVE" — and it
synthesises those signals into structured, actionable intelligence about where the
system is generating noise, why, and how to fix it.

It does not retrain a model. It reasons like a senior compliance strategist: it
reads the data, finds the patterns, and writes a board-ready recalibration report
with specific proposed changes.

Powered by Claude Sonnet via AWS Bedrock, the Evolution Agent transforms analyst
feedback from a passive audit trail into an active improvement engine.

SECTION 3 — WHERE IT SITS IN THE PIPELINE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

To understand the Evolution Agent, you need to understand what happens before it.

Our pipeline processes each new suspicious transaction alert through five stages:

  ┌──────────────────────────────────────────────────────────────────────────┐
  │  ALERT TRIGGERED  (detection rule fires on a transaction)                │
  │         │                                                                │
  │         ▼                                                                │
  │  AGENT 0 — Auto-Labeler  (deterministic pre-screening, no LLM)          │
  │    Immediately scores each COMPLETE alert for false-positive probability │
  │    Verdict: AUTO_TP / AUTO_FP / AUTO_UNCERTAIN                           │
  │         │                                                                │
  │         ▼                                                                │
  │  AGENT 1 — Data Enrichment  (no LLM)                                    │
  │    Joins customer, account, transaction data. Computes stats.            │
  │    Detects anomaly signals. Flags customer/account risk.                 │
  │         │                                                                │
  │         ▼                                                                │
  │  AGENT 2 — Risk Assessment  (Claude Haiku)                               │
  │    Scores 5 risk dimensions. Computes weighted overall risk score.       │
  │    Identifies Key Risk Indicators (KRIs).                                │
  │         │                                                                │
  │         ▼                                                                │
  │  AGENT 3 — Categorisation  (Claude Haiku)                                │
  │    Assigns AML typology (e.g. STRUCTURING, LAYERING, DORMANT_ABUSE).    │
  │    Assigns Risk Tier (CRITICAL / HIGH / MEDIUM / LOW).                  │
  │    Recommends action (ESCALATE / REVIEW / MONITOR / CLOSE).             │
  │         │                                                                │
  │         ▼                                                                │
  │  AGENT 4 — Investigation Summary  (Claude Sonnet)                       │
  │    Generates a full analyst-ready narrative report.                      │
  │         │                                                                │
  │         ▼                                                                │
  │  ANALYST REVIEWS → submits verdict (TRUE_POSITIVE / FALSE_POSITIVE /    │
  │                                     INCONCLUSIVE) + optional notes       │
  │         │                                                                │
  │         ▼                                                                │
  │  AGENT 5 — EVOLUTION AGENT  (Claude Sonnet)                             │
  │    Reads ALL feedback. Identifies FP patterns. Recommends recalibration. │
  └──────────────────────────────────────────────────────────────────────────┘

The Evolution Agent does not run on every alert. It runs on demand — or on a
scheduled cadence — after a sufficient number of analyst verdicts have accumulated
(minimum 3, but meaningful at 20+). This makes it a strategic-layer agent, not
an operational one.

SECTION 4 — THE FEEDBACK LOOP IN DETAIL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The feedback loop has three distinct phases:

  ┌─────────────────────────────────────────────────────────────────┐
  │  PHASE 1: CAPTURE                                               │
  │                                                                 │
  │  When an analyst reviews a triage result, they submit:          │
  │    • analyst_verdict  → TRUE_POSITIVE | FALSE_POSITIVE |        │
  │                         INCONCLUSIVE                            │
  │    • analyst_notes    → free-text reasoning (optional)          │
  │    • override_action  → can override the recommended action     │
  │                                                                 │
  │  This verdict is stored against the alert in SQLite, along      │
  │  with all triage context: the rule that fired, the typology     │
  │  assigned, the risk score, the KRIs, the customer type.         │
  └─────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────┐
  │  PHASE 2: COMPUTE — _compute_statistics()                       │
  │                                                                 │
  │  Before calling the LLM, the Evolution Agent runs a pure        │
  │  Python statistical pass across ALL feedback records.           │
  │                                                                 │
  │  It builds five structured aggregations:                        │
  │                                                                 │
  │  fp_by_rule          — For each detection rule (RULE_HV,        │
  │                         RULE_CRYPTO, etc.), how many verdicts   │
  │                         were FP vs TP vs Inconclusive, and      │
  │                         what is the FP rate?                    │
  │                                                                 │
  │  fp_by_typology      — For each AML typology assigned by        │
  │                         Agent 3 (STRUCTURING, LOW_RISK, etc.),  │
  │                         what fraction of verdicts were FP?      │
  │                                                                 │
  │  fp_by_score_bucket  — Alerts bucketed by overall risk score:   │
  │                         LOW (0.0–0.3), MEDIUM (0.3–0.5),        │
  │                         HIGH (0.5–0.7), CRITICAL (0.7–1.0).     │
  │                         What FP rate does each bucket produce?  │
  │                                                                 │
  │  fp_by_customer_type — FP rates split by Individual vs          │
  │                         Organisation customers.                 │
  │                                                                 │
  │  top_kri_indicators  — Which Key Risk Indicators most           │
  │    _in_fp_alerts        frequently appear in alerts that        │
  │                         turned out to be false positives?       │
  │                         (Top 10 by count.)                      │
  │                                                                 │
  │  These statistics are GROUND TRUTH — computed from real         │
  │  analyst decisions, not model predictions.                      │
  └─────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────┐
  │  PHASE 3: REASON — Claude Sonnet via Bedrock                    │
  │                                                                 │
  │  The computed statistics are passed as a structured prompt to   │
  │  Claude Sonnet with a tightly scoped system instruction:        │
  │                                                                 │
  │  "You are an expert AML system analyst specialising in false    │
  │   positive reduction. Identify patterns that explain why        │
  │   certain alerts are false positives. Generate specific,        │
  │   actionable recalibration recommendations."                    │
  │                                                                 │
  │  Claude returns a structured JSON report containing:            │
  │    • analysis_summary    — 2–3 sentence executive brief         │
  │    • patterns (2–6)      — each FP pattern with root cause,     │
  │                             affected dimension, severity        │
  │    • recalibration_recs  — specific proposed system changes,    │
  │      (2–5, priority-ranked) with expected impact & notes        │
  │    • confidence          — HIGH | MEDIUM | LOW                  │
  │    • data_sufficiency    — tells you if more data is needed     │
  │                                                                 │
  │  After the LLM responds, the agent OVERRIDES three fields       │
  │  with the Python-computed ground truth to prevent LLM drift:    │
  │    result["total_alerts_analyzed"] = total_alert_count          │
  │    result["total_feedback_received"] = total_feedback           │
  │    result["overall_fp_rate"] = overall_fp_rate                  │
  └─────────────────────────────────────────────────────────────────┘

This three-phase design is deliberate: deterministic computation first,
LLM reasoning second, ground-truth anchoring third. The LLM is used for
its pattern synthesis and language capabilities — not for arithmetic.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SECTION 5 — AGENT 0 AND THE AUTO-LABELER: THE PREDICTION ARM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Complementary to the Evolution Agent is Agent 0 — the Auto-Labeler. While Agent 5
analyses historical feedback, Agent 0 makes real-time predictions on new alerts
without waiting for human input.

Agent 0 is entirely deterministic — zero LLM calls. It uses a weighted scoring
model built from the full triage pipeline output of each COMPLETE alert.

HOW AGENT 0 COMPUTES ITS FP PROBABILITY SCORE
──────────────────────────────────────────────

  BASE SCORE = 1.0 − overall_risk_score

  The logic is intuitive: a low-risk alert is more likely to be a false positive.
  This base score is then adjusted by up to 10 modifiers:

  ┌────────────────────────────────────────────────────────────────────────────┐
  │  MODIFIER                          DIRECTION    MAGNITUDE                  │
  ├────────────────────────────────────────────────────────────────────────────┤
  │  1. Recommended action = CLOSE      → +FP        +0.15                    │
  │     Recommended action = ESCALATE   → −FP        −0.20                    │
  │                                                                            │
  │  2. Primary typology = LOW_RISK     → +FP        +0.15                    │
  │     Typology = STRUCTURING/LAYERING → −FP        −0.10                    │
  │     LOW_RISK in secondary typologies→ +FP        +0.06                    │
  │                                                                            │
  │  3. KRI severity adjustments:                                              │
  │     Each CRITICAL KRI              → −FP        −0.08                     │
  │     Each HIGH KRI                  → −FP        −0.04                     │
  │     (capped at −0.25 total)                                                │
  │                                                                            │
  │  4. Anomaly signals:                                                       │
  │     No anomalies detected          → +FP        +0.06                     │
  │     2+ anomaly signals             → −FP        −0.08                     │
  │                                                                            │
  │  5. Customer risk flags:                                                   │
  │     No customer risk flags         → +FP        +0.04                     │
  │     PEP / DECEASED / SANCTIONS     → −FP        −0.20                     │
  │                                                                            │
  │  6. Rule base-rate FP deltas:                                              │
  │     RULE_DECEASED                  → −FP        −0.35 (almost never FP)  │
  │     RULE_PEP                       → −FP        −0.10                     │
  │     RULE_HV                        → +FP        +0.05 (often routine)    │
  │     RULE_DORMANT                   → +FP        +0.05                     │
  │     RULE_CASH                      → +FP        +0.03                     │
  │                                                                            │
  │  7. Categorisation confidence:                                             │
  │     Confidence < 40%               → +FP        +0.08                     │
  │     Confidence ≥ 75%               → −FP        −0.06                     │
  │                                                                            │
  │  8. Investigation confidence level:                                        │
  │     LOW investigation confidence   → +FP        +0.05                     │
  │     HIGH investigation confidence  → −FP        −0.08                     │
  │                                                                            │
  │  9. LLM risk tier escalation:                                              │
  │     LLM classified HIGHER tier     → +FP        +0.08                     │
  │     than score alone suggests                                              │
  └────────────────────────────────────────────────────────────────────────────┘

  FINAL FP PROBABILITY = Base + sum(all modifiers), clamped to [0.0, 1.0]

  VERDICT THRESHOLDS:
    fp_probability ≥ 0.65  →  AUTO_FP       (system predicts false positive)
    fp_probability ≤ 0.25  →  AUTO_TP       (system predicts true positive)
    otherwise              →  AUTO_UNCERTAIN (human review needed)

The reason Agent 0 exists alongside Agent 5 is to close the real-time gap.
Agent 5 generates reports periodically, but Agent 0 labels every alert the
moment it is complete — giving analysts an immediate first-pass signal before
they even open the alert.

SECTION 6 — AGENT 2: THE RISK SCORING ENGINE (WEIGHTS IN DETAIL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The overall risk score that underpins both Agent 0 and the Evolution Agent is
produced by Agent 2 — the Risk Assessment Agent.

It scores 5 dimensions and combines them using fixed weights:

  ┌─────────────────────────────────────────────────────────────────────────┐
  │  DIMENSION            WEIGHT   WHAT IT MEASURES                        │
  ├─────────────────────────────────────────────────────────────────────────┤
  │  Transaction Risk      30%     Amount, type (crypto, cash, wire),       │
  │                                currency, anomalies (round amounts,      │
  │                                just-below-threshold structuring)        │
  │                                                                         │
  │  Customer Risk         25%     PEP status, deceased flag, new customer  │
  │                                (<6 months, <1 year), organisation type  │
  │                                                                         │
  │  Account Risk          15%     Dormant/inactive status, new account     │
  │                                (<90 days), business account,            │
  │                                multi-account customer                   │
  │                                                                         │
  │  Behavioural Risk      20%     Anomaly signals vs historical baseline:  │
  │                                amount anomaly, new currency first seen, │
  │                                new transaction type first seen          │
  │                                                                         │
  │  Network Risk          10%     Destination flags: internal transfer,    │
  │                                cross-customer, dormant destination,     │
  │                                PEP destination, first-time counterparty │
  └─────────────────────────────────────────────────────────────────────────┘

  OVERALL RISK SCORE = (Tr × 0.30) + (Cr × 0.25) + (Br × 0.20) +
                       (Ar × 0.15) + (Nr × 0.10)

The agent uses a two-step process:
  Step 1: Compute deterministic baseline scores from enriched data (pure Python)
  Step 2: Send baselines + full alert context to Claude Haiku for nuanced LLM
          re-scoring, which can adjust each dimension based on contextual reasoning

If the LLM's final score deviates by more than 0.15 from the Python-computed
baseline, the system trusts the computed score. This guards against LLM drift
while still allowing meaningful contextual adjustments.

The overall risk score is then stored on the alert and flows into:
  → Agent 3 (risk tier classification)
  → Agent 0 (FP probability base score)
  → Agent 5 (fp_by_score_bucket statistics)

SECTION 7 — HOW THE SYSTEM LEARNS FROM ITSELF
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This is the key differentiator. Let's walk through a concrete learning cycle.

─────────────────────────────────────────────────────────────
CYCLE 1 — System goes live. No feedback exists.
─────────────────────────────────────────────────────────────

  • Alerts are triaged by Agents 1–4.
  • Agent 0 predicts verdicts using its built-in heuristic weights.
  • Analysts review alerts and submit their verdicts.
  • Feedback accumulates in SQLite.
  • Evolution Agent cannot run yet (<3 records). Returns empty state.

─────────────────────────────────────────────────────────────
CYCLE 2 — 20+ feedbacks submitted. First Evolution run.
─────────────────────────────────────────────────────────────

  • _compute_statistics() processes all feedback.

  Suppose the data shows:
    RULE_HV:    18 alerts, 14 FALSE_POSITIVE → FP rate = 77.8%
    LOW_RISK typology: 9 alerts, 8 FALSE_POSITIVE → FP rate = 88.9%
    Score bucket 0.0–0.3: 11 alerts, 10 FALSE_POSITIVE → FP rate = 90.9%
    KRI "AMOUNT_WITHIN_NORMAL_RANGE" appears in 12 of the 14 RULE_HV FPs

  • Claude Sonnet receives these statistics and generates:

    Pattern detected:
      "RULE_HV is triggering high-value alerts for routine payroll and
       business payment transactions. The AMOUNT_WITHIN_NORMAL_RANGE KRI
       appearing in 85% of RULE_HV false positives confirms these are
       expected business operations for corporate customers."

    Recommendation (Priority 1):
      Target: RULE_HV threshold
      Current: Flags ALL transactions > $10,000 AUD
      Proposed: Exclude transactions within 2 standard deviations of the
                account's historical average for established accounts (>12 months)
      Expected impact: Reduce FP rate by ~40% for RULE_HV
      Notes: Apply only to accounts with 12+ months of transaction history
             and no prior TP verdicts. Review quarterly.

    Recommendation (Priority 2):
      Target: LOW_RISK typology auto-close
      Current: LOW_RISK alerts are sent to analyst queue
      Proposed: Auto-close LOW_RISK alerts where risk score < 0.3 and
                no CRITICAL/HIGH KRIs present
      Expected impact: Reduce analyst workload by ~25%

  • Evolution report saved to SQLite (evolution_runs, evolution_patterns,
    evolution_recommendations tables).
  • Report displayed on the Evolution dashboard page.

─────────────────────────────────────────────────────────────
CYCLE 3 — Recommendations reviewed by compliance team.
          Some are applied. More feedback accumulates.
─────────────────────────────────────────────────────────────

  • If the RULE_HV threshold change is applied, the system now raises
    fewer RULE_HV alerts for routine corporate accounts.
  • New alerts are triaged under the updated logic.
  • Analysts continue submitting verdicts.
  • Next Evolution run compares the new FP rate against the previous run.

─────────────────────────────────────────────────────────────
CYCLE N — Compounding improvement
─────────────────────────────────────────────────────────────

  • Each Evolution run appends a new row to evolution_runs, tracking:
      - total alerts, total labeled, TP/FP counts, FP rate
      - patterns found, recommendations generated
  • Patterns that appear across multiple runs are tracked in
    evolution_patterns with a seen_count field — persistent patterns
    that survive multiple cycles demand higher priority.
  • The dashboard's Evolution page shows the FP rate trend over runs,
    allowing the team to see measurable improvement over time.

The system does not modify its own code or weights automatically. That is
intentional — regulatory environments require human sign-off on material
system changes. The Evolution Agent generates the intelligence; humans apply
the changes. This is responsible AI design.

SECTION 8 — DATA PERSISTENCE & AUDIT TRAIL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Every piece of the feedback loop is persisted in SQLite with full lineage:

  alerts table
    → stores every alert with all triage outputs, analyst verdicts,
      predicted_verdict (Agent 0), predicted_fp_probability, predicted_reason

  evolution_runs table
    → one row per Evolution Agent invocation
    → tracks: run_number, timestamp, alert counts, FP rate, patterns/recs found

  evolution_patterns table
    → one row per unique pattern identified
    → tracks across runs: first_seen_run, last_seen_run, seen_count, status
    → a pattern that keeps reappearing despite no action is flagged as persistent

  evolution_recommendations table
    → one row per recommendation
    → tracks: priority, category, recommendation text, rationale
    → when applied: applied_at, applied_by, outcome_delta (measured FP improvement)

  audit_log table
    → immutable append-only log of all system events
    → required for regulatory compliance

On system restart, all alerts are reloaded from SQLite into memory,
and Agent 0 re-scores any COMPLETE alerts that lack a predicted verdict.
Nothing is lost between restarts.

SECTION 9 — WHAT MAKES THIS DIFFERENT FROM A STANDARD ML MODEL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A common question: "Why not just retrain a classifier on analyst feedback?"

Four reasons:

  1. EXPLAINABILITY
     Regulators (AUSTRAC, APRA, FinCEN) require that compliance decisions be
     explainable in plain English. A retrained neural network cannot explain
     why it changed its decision. Our Evolution Agent produces a written report
     with cited evidence, named patterns, and described root causes that a
     compliance officer can read, challenge, and sign off on.

  2. DATA VOLUME
     Retraining a robust classifier requires thousands of labelled examples.
     In the early months of a deployment, you may have dozens of feedback records.
     The Evolution Agent's LLM-reasoning approach works meaningfully with as few
     as 20–30 verdicts.

  3. HUMAN IN THE LOOP — BY DESIGN
     The system surfaces recommendations, not automatic changes. This respects
     governance frameworks where material system changes require approval.
     The Agent generates the case; humans make the call.

  4. BROAD PATTERN TYPES
     A classifier learns the correlation between features and outcomes.
     The Evolution Agent can surface qualitative patterns — "analysts consistently
     override ESCALATE recommendations for Organisation-type customers with
     RULE_HV" — that a feature-weight model would not express in human terms.

SECTION 10 — SUMMARY: THE EVOLUTION AGENT IN ONE PAGE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  WHAT IT IS:
    A closed-loop intelligence agent that analyses accumulated analyst feedback
    to identify false positive patterns and recommend system recalibration.

  WHAT IT REPLACES:
    Manual annual rule reviews. Ad-hoc analyst complaints. Static configuration
    that drifts further from reality every day.

  HOW IT WORKS:
    Step 1 — Capture analyst verdicts (TRUE_POSITIVE / FALSE_POSITIVE /
             INCONCLUSIVE) for every triaged alert.
    Step 2 — Compute ground-truth statistics: FP rates by rule, typology,
             risk score bucket, customer type, and KRI indicator.
    Step 3 — Pass statistics to Claude Sonnet to identify root-cause patterns
             and generate prioritised recalibration recommendations.
    Step 4 — Store report with full audit lineage. Present on dashboard.
    Step 5 — Compliance team reviews, approves, and applies changes.
    Step 6 — Cycle repeats. FP rate trends downward over time.

  THE NUMBERS IT TRACKS:
    • Overall FP rate across all labelled alerts
    • Per-rule FP rate (RULE_HV, RULE_CRYPTO, RULE_PEP, etc.)
    • Per-typology FP rate (STRUCTURING, LOW_RISK, LAYERING, etc.)
    • Per-score-bucket FP rate (LOW / MEDIUM / HIGH / CRITICAL bands)
    • Top KRI indicators that most frequently appear in false positives

  THE SAFEGUARDS:
    • Minimum 3 feedback records required to generate any analysis
    • LLM-generated counts/rates are overridden by Python-computed ground truth
    • No automatic system changes — all recommendations require human approval
    • Full audit trail in SQLite — immutable event log

  THE COMPOUNDING EFFECT:
    • Each Evolution run builds on the previous one
    • Persistent patterns (seen across multiple runs) are escalated
    • Applied recommendations track their outcome delta (measured FP improvement)
    • The system gets demonstrably smarter with every analyst interaction

  THE BUSINESS CASE:
    Industry FP rates: 85–95%
    Target FP rate with Evolution Agent after 6 months: <50%
    Analyst time saved per alert reviewed: 70% reduction (pipeline effect)
    Regulatory confidence: Full audit trail, human-approved changes,
                           explainable recommendations
